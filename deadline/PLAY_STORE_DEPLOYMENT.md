# Deploying Deadlines&Notes to Google Play

This document is a deployment runbook tailored to this app. Keep it next to the
repo so future releases repeat the same steps.

## 0. One-time prerequisites

- A Google Play Console account (developer registration fee) and a verified
  developer profile.
- A Google Cloud project with the **Google Drive API** enabled (only needed
  because Drive sync is offered). See section 6.
- Java 17 + Android SDK (already present — `flutter doctor` is green apart
  from accepted licenses, which are now accepted).
- The upload keystore created for this app: `android/upload-keystore.jks`
  (alias `upload`). **Back up this file and `android/key.properties`
  somewhere safe (password manager / encrypted backup).** If you lose them you
  cannot publish updates — Play cannot reset an upload key without a lengthy
  support request.

## 5. Data safety form (fill carefully — mismatches cause rejection)

The app stores tasks and notes **on the device only** by default. Two optional
sync paths exist. Declare accordingly:

- **Data collected:** optional `User IDs` (Google account identifier) and
  `App activity` → `Other user-generated content` (tasks/notes) **only when**
  sync is enabled. Collection is optional and not required for core function.
- **Data sharing:** **No** — nothing is shared with third parties for
  advertising/analytics. (When Drive sync is used, data is written to the
  *user's own* Google Drive under their own account; that's user-directed and
  does not count as sharing by your app.)
- **Data handling:** data can be deleted by the user (turn off sync / delete app
  / clear app data). Encryption in transit: yes (HTTPS to Drive/Laravel).
  Encryption at rest: device-level only (no extra app encryption).
- **Privacy policy URL:** paste your hosted policy URL here.

Declared permissions that need justification in this form / review:
- `POST_NOTIFICATIONS` — for deadline reminders (user-facing, optional).
- `SCHEDULE_EXACT_ALARM` / `USE_EXACT_ALARM` — reminders must fire at the
  exact deadline time. **In Play Console, fill the "Exact alarm permission"
  declaration form with the justification:** "The app schedules local reminder
  notifications for user-created deadlines at exact user-chosen times."
- `RECEIVE_BOOT_COMPLETED` — reschedule reminders after reboot (no data
  collected).
- `USE_FULL_SCREEN_INTENT` — show the closest-due reminder over the lock
  screen. **Fill the full-screen-intent declaration form** with: "Show an
  urgent deadline reminder over the lock screen so the user sees it immediately
  when due." (Play scrutinises this; if rejected, remove the permission and
  the lock-screen behaviour.)
- `INTERNET` — optional sync only.

## 6. Google Cloud — make Google Drive sync work in the released app

This is the step most people get wrong. Google Sign-In on Android verifies the
app by **package name + signing-certificate SHA-1**. The Play Store **re-signs**
your app with its own app-signing key, so the SHA-1 that matters in production
is **not** your upload keystore's SHA-1.

### 6.1 Upload keystore SHA-1 (use for sideloaded/internal testing)

```bash
keytool -list -v -keystore android/upload-keystore.jks -alias upload \
  -storepass "$(grep -oP 'storePassword=\K.*' android/key.properties)" 2>/dev/null \
  | grep -E "SHA1|SHA256"
```

Recorded for this keystore:
- SHA-1:  `B2:37:A5:D9:6E:10:68:F7:16:3D:81:C7:B2:2D:4A:B2:34:16:7F:13`
- SHA-256:`80:C7:9A:0A:AE:14:19:F6:9D:1E:DF:81:58:61:A0:97:61:C5:30:75:65:8C:67:03:DA:94:2D:44:D6:E3:E2:30`

### 6.2 Play app-signing SHA-1 (this is the one production needs)

After you upload the **first** AAB in Play Console → **Release → Production**
(or Internal testing → Create release → upload AAB), Google creates the app
signing key. Then go to:

Play Console → your app → **Release → Setup → App integrity → App signing**.

Copy the **SHA-256 (and SHA-1) certificate fingerprints** shown under
"App signing key certificate". These are the fingerprints of the cert Play uses
to sign the APKs users actually install.

### 6.3 Create the OAuth clients

Google Cloud Console → your project → **APIs & Services → Credentials**:

1. Enable **Google Drive API**.
2. **OAuth consent screen**:
   - User type: External.
   - Add the Drive scopes? Scopes are requested at runtime by the app
     (`https://www.googleapis.com/auth/drive.appdata`). You only need to
     publish the app as verified eventually; while testing add your own Google
     account as a **Test user** so sign-in works without verification.
   - App name, support email, developer contact.
3. **Credentials → Create credentials → OAuth client ID → Android**:
   - Name: `Deadlines&Notes (upload key)`
   - Package name: `com.deadline.app.deadline`
   - SHA-1: paste the **upload keystore** SHA-1 from 6.1 (for sideloaded builds).
   - Create another OAuth client ID → Android named
     `Deadlines&Notes (play signing)` with the **Play app signing** SHA-1 from
     6.2. (You can hold multiple Android clients for one package.)
4. **Create credentials → OAuth client ID → Web application** (optional,
   needed only if you also want a server-side client ID; not required for
   this app since Drive access is client-side).

No `google-services.json` is needed — the `google_sign_in` plugin matches by
package name + fingerprint automatically.

### 6.4 Testing before verification

Until OAuth consent is verified, only test users can sign in. Keep your own
account as a test user. Avoid shipping Drive sync as a headline feature until
verification is complete, or users will see "Access blocked".

## 7. Store listing assets you must provide

Play Console → **Store presence → Main store listing** needs:

- **Short description** (≤ 80 chars), e.g.:
  `Offline-first task & note tracker sorted by what's due next. Optional sync.`
- **Full description** (≤ 4000 chars) — reuse/trim the README intro + feature
  list.
- **App icon**: 512×512 PNG, 32-bit, ≤ 1024 KB. The current launcher icon is
  generated from `assets/icon/icon.png`; export a 512×512 version (or run a
  quick resize) and upload.
- **Feature graphic**: 1024×500 PNG/JPG, ≤ 1 MB (no transparency).
- **Screenshots**: at least 2 phone screenshots (16:9 or 9:16), up to 8. Take
  from a device/emulator of the list, a task card close-up, the widget, sync
  sheet, settings. Recommended also a 7-inch and 10-inch tablet set if you want
  tablet merchandising.
- **Video** (optional): YouTube URL.
- Privacy policy URL: paste yours.

## 8. Upload and release

1. Play Console → **Release → Internal testing → Create new release**.
2. Upload `app-release.aab`. Wait for processing (a few minutes). Resolve any
   warnings (the console will flag permissions declarations you haven't filled —
   do those first).
3. Release name = `1.0.0 (1)`. Add release notes.
4. Save → **Review release** → fix any blockers → **Start rollout to Internal
   testing**.
5. Install from the internal-testing link on a real device and run through:
   create task, notification scheduling, widget, and (if using Drive) sign-in +
   first sync. This validates the Play-signed build + OAuth fingerprint before
   going public.
6. Promote to **Closed testing** (optional, recommended for a first release)
   then **Production**.

## 9. After launch

- Watch **Play Console → Quality → Android vitals** (crashes/ANRs). The debug
  symbols shipped with the AAB keep stack traces readable.
- Ratings/reviews response.
- For updates: bump versionCode, rebuild AAB, upload to a new release track
  (internal → production). Never rebuild with a different keystore.
- If you ever enable R8/minification (`minifyEnabled true` in
  `android/app/build.gradle.kts`), add ProGuard rules for `sqflite`,
  `flutter_local_notifications`, and `home_widget`, then re-test thoroughly.

## 10. Common Play rejection causes for this app (pre-empt them)

- **SCHEDULE_EXACT_ALARM without justification** → fill the declaration form
  (section 5).
- **USE_FULL_SCREEN_INTENT without justification** → fill the declaration form.
- **Drive scope verification** → appDataFolder is a restricted scope; ship
  with test users first, submit verification before broad launch.
- **Missing privacy policy / wrong URL** → ensure URL loads and matches the
  data-safety answers.
- **Target SDK too low** → already 36, fine.
- **Impersonating Google** → app name "Deadlines&Notes" is fine, but don't use
  Google logos in the listing.
- **Crashes on launch on the Play-signed build** → almost always the Google
  Sign-In fingerprint mismatch (section 6) or a missing permission. Test the
  internal-testing build before promoting.
